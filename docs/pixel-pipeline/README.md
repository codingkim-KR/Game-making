# 주인공 도트 파이프라인 — 1차 캡처 비교 (일반검 3연격)

2026-11-16, Claude 작성.

## 무엇을 했나

Motion Lab의 실제 플레이어 컨트롤러와 HeroVisual을 게임과 똑같이 구동하면서, 물리 1틱(1/60초)마다 한 장씩 PNG로 저장하는 캡처 도구를 만들었다. 입력 버퍼, 연계 예약, 전환 보간, 손 IK가 모두 게임 그대로 들어가므로, 캡처한 동작이 게임 안 동작과 어긋나지 않는다. 카메라는 정사영이고 플레이어 발 위치에 고정되어 있어서, 스프라이트에는 자세만 담기고 몸의 이동은 엔진이 맡는다.

일반검 3연격은 연계 입력부터 대기 자세로 돌아올 때까지 61틱(약 1.02초)이고, 대기 24틱을 더해 86장을 캡처했다. 메타데이터에서 틱 간격이 정확히 1/60초인 것을 확인했다. 단계별 구간은 다음과 같다.

1타 준비 1–4, 타격 5–7, 회복 8–13 / 2타 준비 14–19, 타격 20–23, 회복 24–28 / 3타 준비 29–36, 타격 37–42, 회복 43–61 / 대기 62–86 (Aseprite 프레임 번호, 1부터)

## 네 가지 렌더링 방식 비교

같은 86틱을 네 방식으로 뽑아 비교했다. 픽셀 밀도는 일단 1m당 56.25px로 두었다. 지금 연습장 화면(세로 6.4m)을 640×360 해상도로 보여 주는 값이고, 이때 주인공 키가 약 103px이다. 최종 게임 해상도가 정해지면 이 값만 바꾸면 된다.

86장 전체에서 센 서로 다른 색의 수와 반투명 픽셀 비율은 이렇다.

- A. 크게 렌더링(MSAA 2x)한 뒤 절반으로 축소: 13,535색, 반투명 22.3%
- B. 최종 크기로 직접 렌더링, 기존 부드러운 명암: 1,324색, 반투명 0%
- C. 최종 크기 + 명암 3단계(hero_toon_pixel): 39색, 반투명 0%
- D. C + 팔레트 고정 + 1px 외곽선: 40색, 반투명 0%

경계가 흐려지는 원인은 두 단계에 있었다. 첫째, 크게 렌더링한 뒤 줄이면 축소 필터와 MSAA가 테두리에 반투명 중간색을 만든다. A에서는 보이는 픽셀의 5분의 1 이상이 반투명이었다. 최종 크기로 바로 렌더링하면(B) 이 값이 0이 된다. 둘째, 기존 툰 셰이더는 명암 경계를 smoothstep으로 부드럽게 넘긴다. 스프라이트 크기에서는 그 경계 하나가 여러 픽셀에 걸친 미세한 색 단계로 펼쳐져서, B에도 1,300개가 넘는 색이 남는다. 경계를 계단식으로 바꾸면(C) 재질 색 × 밝기 3단계만 남아 39색이 된다. 손으로 다듬을 수 있는 크기의 팔레트다.

비교 그림은 `compare_sword_combo.png`(주요 4프레임), `zoom_frame20.png`(2타 타격의 머리·어깨 10배 확대), 수치는 `metrics.json`에 있다.

## 남은 문제

명암 경계를 계단식으로 바꾸면 저폴리곤 모델의 면 방향이 경계 근처에서 들쭉날쭉한 것이 그대로 드러난다. C에서 상하좌우 이웃과 색이 모두 다른 외톨이 픽셀이 프레임당 평균 118개(최대 209개) 나왔다. 기존 셰이더 주석이 "작은 얼굴과 손에서 깜빡임을 피하려고 부드러운 경계를 썼다"고 적은 바로 그 현상이다. 이 중 일부는 눈, 버클, 칼끝처럼 원래 있어야 하는 1픽셀 디테일이고, 나머지가 손으로 정리해야 할 잡티다. 다음 단계에서 법선을 매끄럽게 하거나 명암 경계에 약간의 여유를 주는 방법을 시험해, 손작업 전에 잡티를 줄일 수 있는지 볼 예정이다.

Aseprite는 프레임 길이를 정수 밀리초로 저장하기 때문에 1/60초가 16ms로 저장된다. Aseprite 안에서 미리보기를 하면 약 4% 빠르게 재생되지만, 게임에서는 엔진 타이밍을 쓰므로 영향이 없다.

## 산출물

- `art/hero/sword_combo_60fps.aseprite` — D 방식 86프레임, 위 구간이 태그로 붙어 있다. 키프레임을 고를 때 태그별로 보면 된다.
- `motion-lab/tools/capture_motion.gd` — 캡처 도구. 무기, 동작, 픽셀 밀도, MSAA, 명암 방식을 인자로 받는다.
- `motion-lab/shaders/hero_toon_pixel.gdshader` — 캡처 전용 계단식 명암 셰이더. 게임 셰이더는 바꾸지 않았다.
- `motion-lab/tools/pixel_post.py` — 반투명 제거, 시퀀스 공통 팔레트 고정, 외곽선.
- `motion-lab/tools/make_aseprite.lua` — 캡처 폴더를 태그 달린 .aseprite로 묶는다.
- `motion-lab/tools/compare_variants.py` — 위 비교 그림과 수치를 다시 만든다.
- `motion-lab/tools/asep.py` — aseprite-mcp 도구를 셸에서 부르는 클라이언트.

## 다시 만드는 방법

```bash
cd motion-lab
G=Godot_v4.6.3   # Linux에서는 xvfb-run -a 를 앞에 붙인다
$G --path . --rendering-driver opengl3 --fixed-fps 60 --script res://tools/capture_motion.gd -- \
  --weapon=0 --sequence=combo --toon=hard --msaa=0 --out=res://capture_raw/sword_combo_hard
python3 tools/pixel_post.py capture_raw/sword_combo_hard capture_raw/sword_combo_pixel
aseprite -b --script-param dir=capture_raw/sword_combo_pixel \
  --script-param out=../art/hero/sword_combo_60fps.aseprite --script tools/make_aseprite.lua
```

`capture_raw/`는 용량이 커서 저장소에 올리지 않는다.

기존 자동 검사 3종(63 + 13 + 48개)은 이번 추가 후에도 모두 통과했다.

## 정해야 할 것

1. 최종 게임 화면 해상도와 주인공 키(픽셀). 지금은 640×360, 약 103px로 가정했다.
2. 재생 프레임 수. 60틱 원본 중 어떤 틱을 키프레임으로 남길지, 구간별로 몇 틱씩 유지할지.
